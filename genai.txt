## FCFS

**Before:** Empty stub; no clock or per-process metrics.

**After:** `fcfs(List<Process> processes)` (same shape as `sjf(List<Process> …)`):

- Reset every process.  
- Walk the list in order (no sort — matches your “no sorting necessary” note).  
- Advance a `clock` by each process’s `remainingTime` (full burst on first pass).  
- Call `recordCompletion(clock)` when each process finishes.

## Round Robin

**Before:** Only `timeQuantum = 2`; no queue or time tracking.

**After:** `roundRobin(List<Process> processes)`:

- Reset all processes.  
- `LinkedList` ready queue in input order.  
- Each step: run `min(quantum, remainingTime)`, bump `clock`, `decreaseBurstTime(slice)`.  
- If `remainingTime == 0` → `recordCompletion(clock)`; else re-enqueue.

Preemption is modeled by re-queuing processes that still have `remainingTime > 0`.

**Cursor**

The clock is doing real work — it’s just easy to miss because nothing prints it.

In FCFS, each process runs only after every earlier one has finished. The variable is **simulated time**: when the current process exits, the clock equals its **completion time**. That value goes straight into `recordCompletion(clock)`, which sets:

- `completion_time` / `turnaround_time` → that clock value (arrival at 0)
- `waiting_time` → `clock − burstTime` (time spent waiting before it ran)

Example with bursts 5, 3, 1: clock goes 5 → 8 → 9. Process 2’s turnaround is **8**, not 3; its waiting time is **5**. Without adding each process’s service time onto a running total, every process would look like it finished at its own burst length and waiting times would be wrong.

What you *can* simplify:

- After `resetForScheduling()`, `getRemainingTime()` equals `getBurstTime()`, so `clock += p.getBurstTime()` is the same idea for FCFS.
- FCFS never preempts, so you don’t need a separate “tick” loop — one addition per process is enough.

So the **running total** matters; the name `clock` is optional. If you removed it and didn’t pass an equivalent cumulative finish time into `recordCompletion`, the averages from `calcTimes` would no longer reflect FCFS.

Yes — for your setup (every process in the list at time 0, fixed order, no new arrivals), a **queue and a circular scan are the same policy**. Skipping the `Queue` is reasonable and often reads more clearly in a small student project.

### What the queue is doing

`LinkedList` + `poll`/`offer` is just: **take the next not-finished process in rotation, run up to the quantum, put it back if it still has work**. That’s RR’s fairness rule, not a requirement that you use a queue type.

### Scan-based RR (what you’re describing)

Use one global clock and repeat full passes over `processes` until nothing is left:

```java
final int timeQuantum = 2;
// reset all processes first
int clock = 0;

while (/* at least one process !isCompleted() */) {
    for (Process p : processes) {
        if (p.isCompleted()) continue;

        int slice = Math.min(timeQuantum, p.getRemainingTime());
        clock += slice;
        p.decreaseBurstTime(slice);

        if (p.getRemainingTime() == 0) {
            p.recordCompletion(clock);
        }
    }
}
```

The `while` can be `while (!allCompleted(processes))` or a small inline loop that counts incomplete processes — same idea.

Here **`isCompleted` (or `remainingTime == 0`) replaces “is this still in the ready queue?”** You don’t need a separate `current` reference beyond the `for` loop variable.

### Comparison

| | Queue version | While + for scan |
|--|----------------|------------------|
| **Correctness** (your assumptions) | Same | Same |
| **Concepts** | Ready queue (OS-flavored) | Round-robin “go around the table” |
| **Extra types** | `Queue`, `LinkedList` | None beyond what you already have |
| **Variables** | `ready`, `current`, `slice`, `clock` | `slice`, `clock` (+ completion check) |

The scan version is usually **shorter and easier to explain** on a write-up: “each round, visit every process in order; skip finished ones; run at most one quantum.”

### Small caveats (not blockers for your project)

1. **`isCompleted` vs `remainingTime`** — Either works for skipping; `isCompleted` matches your field naming. Just don’t mark complete until after the last slice (as you do in `recordCompletion`).

2. **Order** — Both implementations must use the **same list order** as your input (e.g. `process.txt`). Queue initialized from the list and repeated `for` over the list do that.

3. **Later extensions** — If you add **arrival times** or processes that **join mid-simulation**, a real ready queue (or a queue built each tick from “arrived and not complete”) fits better. For static “everyone at 0,” the scan loop is fine.

So your instinct is sound: the queue version is robust and textbook-accurate, but **a `while` + `for` with `isCompleted` is more concise and fits your `Process` model well** without changing RR behavior for this assignment.
